> План будущей синхронизации по Architecture v3. Web Runtime показывает Deck через общий Renderer и не редактирует проект. Примеры сообщений ниже концептуальные; внедрение протокола выполняется отдельной задачей.

# RADISH DECK

# WEBSOCKET DOCUMENTATION

Версия:

Alpha 0.1.0

------------------------------------------------------------------------

# 1. Назначение

WebSocket используется для связи между:

    Radish Deck Server

            |

        WebSocket

            |

    Radish Deck Client

Главная задача:

Передавать данные в реальном времени.

Используется для:

-   обновления интерфейса;
-   отправки команд;
-   получения состояния;
-   синхронизации клиентов.

------------------------------------------------------------------------

# 2. Главный принцип

REST API используется для:

-   получения данных;
-   настройки;
-   CRUD операций.

WebSocket используется для:

-   событий;
-   быстрых обновлений;
-   команд в реальном времени.

------------------------------------------------------------------------

# 3. Подключение

Адрес:

    ws://<RADISH_DECK_IP>:8080/ws

Пример:

    ws://10.16.0.20:8080/ws

Для удалённых клиентов и LAN-проверок используется выбранный доступный IP сервера. Loopback допустим для локального запуска и изолированных проверок, но не проверяет доступ с другого устройства.

------------------------------------------------------------------------

# 4. Жизненный цикл клиента

Подключение:

    Client

    ↓

    Connect

    ↓

    Authenticate

    ↓

    Receive Layout

    ↓

    Receive State

    ↓

    Ready

------------------------------------------------------------------------

# 5. Client Connected

Когда клиент подключается:

Событие:

``` json
{
"type":"client_connected",
"client_id":"phone",
"device":"mobile"
}
```

------------------------------------------------------------------------

# 6. Client Disconnected

Когда клиент отключается:

``` json
{
"type":"client_disconnected",
"client_id":"phone"
}
```

------------------------------------------------------------------------

# 7. Layout Update

Сервер отправляет новый интерфейс.

Пример:

``` json
{
"type":"layout_update",
"page":"Home",
"version":1
}
```

Клиент должен:

-   обновить страницу;
-   обновить элементы.

------------------------------------------------------------------------

# 8. State Update

Обновление состояния элемента.

Пример:

``` json
{
"type":"state_update",
"element_id":5,
"state":{
"status":"running"
}
}
```

Примеры:

Docker:

    Running

Application:

    Started

System:

    CPU 35%

------------------------------------------------------------------------

# 9. Client Action

Клиент отправляет команду:

``` json
{
"type":"execute",
"element_id":5,
"action":"docker.restart"
}
```

Сервер:

1.  Проверяет действие.
2.  Запускает Action Engine.
3.  Возвращает результат.

------------------------------------------------------------------------

# 10. Action Result

Успешное выполнение:

``` json
{
"type":"action_result",
"success":true,
"message":"Completed"
}
```

Ошибка:

``` json
{
"type":"action_result",
"success":false,
"error":"Failed"
}
```

------------------------------------------------------------------------

# 11. Multiple Clients

Radish Deck поддерживает несколько клиентов.

Пример:

    Desktop

    +

    Phone

    +

    Tablet

    +

    Browser

Все используют общую модель Deck; отображение учитывает Device Profile.

------------------------------------------------------------------------

# 12. Synchronization

Desktop Designer создаёт и изменяет проект. Deck остаётся общей моделью.
Server передаёт изменения Deck и состояния клиентам; общий Renderer
отображает их с учётом Device Profile. Способ хранения не определяет
авторство проекта: обязательная Database не является условием этой схемы.
Все клиенты используют общий Deck, но могут выбирать разные профили.
# 13. Heartbeat

Клиент периодически отправляет:

``` json
{
"type":"heartbeat"
}
```

Сервер отслеживает:

-   подключение;
-   время последнего ответа;
-   состояние клиента.

------------------------------------------------------------------------

# 14. Ошибки соединения

Клиент должен обрабатывать:

-   потерю соединения;
-   повторное подключение;
-   ошибку сервера.

------------------------------------------------------------------------

# 15. Безопасность

Будущее:

-   pairing;
-   токены;
-   авторизация;
-   шифрование.

------------------------------------------------------------------------

# 16. Правила разработки

Запрещено:

-   отправлять команды напрямую в Windows;
-   хранить состояние только в клиенте;
-   создавать отдельный протокол для каждого клиента.

Правильно:

    Client

    ↓

    WebSocket

    ↓

    Server

    ↓

    Action Engine

    ↓

    Executor

------------------------------------------------------------------------

# 17. Цель WebSocket системы

Создать стабильную двустороннюю связь.

Radish Deck должен работать одинаково для:

-   Desktop;
-   Web;
-   Mobile;
-   Tablet.
