# RadishDeck Element Model

Версия: целевая модель Designer v3

Этот документ описывает проектируемую модель `Element` для будущего
RadishDeck Designer. Источниками направления являются `VISION.md` (Vision
v3), `ARCHITECTURE.md` (Architecture v3) и `DESIGNER_SPEC.md`.

Модель является спецификацией будущего Designer. Она не означает, что все
перечисленные поля и типы уже реализованы в текущем прототипе.

## 1. Общая идея

`Element` — универсальный объект интерфейса панели управления. Он описывает
не только нажатие кнопки, но и то, что пользователь видит на Canvas, как
объект располагается, как выглядит, как реагирует на события и какое действие
может выполнять.

Целевая структура:

```text
Element
├── Identity
│   ├── Id
│   ├── Name
│   └── Type
│
├── Layout
│   ├── Position X/Y
│   ├── Width
│   ├── Height
│   ├── Layer
│   └── Alignment
│
├── Content
│   ├── Text
│   ├── Image
│   ├── Icon
│   ├── Logo
│   └── Media
│
├── Appearance
│   ├── Background
│   ├── Color
│   ├── Border
│   ├── Radius
│   ├── Shadow
│   ├── Font
│   └── Opacity
│
├── Behavior
│   ├── Hover
│   ├── Click
│   ├── Animation
│   └── States
│
└── Action
    ├── Process
    ├── URL
    ├── Script
    ├── Command
    └── Future Plugin
```

## 2. Identity

`Identity` uniquely identifies an element in a Deck and describes его тип.

- `Id` — стабильный идентификатор элемента;
- `Name` — имя, показываемое в Designer и доступное пользователю;
- `Type` — тип элемента, например `Button`, `Text`, `Image` или `Container`.

Тип определяет доступные редакторы Content, Appearance и Behavior. Он не
должен определять способ выполнения Action.

## 3. Layout и Canvas

Элемент располагается на Canvas. `Layout` описывает:

- координаты `X` и `Y`;
- `Width` и `Height`;
- `Layer` — порядок отрисовки;
- `Alignment` — правила выравнивания.

Canvas и Device Profile определяют рабочую область, размеры, ориентацию и
правила отображения для Desktop, Tablet, Mobile и Custom. Layout не должен
быть ограничен моделью `Grid-only`. Сетка может использоваться как инструмент
выравнивания в Designer, но не является основной моделью позиционирования.

## 4. Content

`Content` содержит данные, из которых Renderer строит визуальное содержимое:

- текст;
- изображение;
- иконку;
- логотип;
- медиа-ресурс.

Набор полей зависит от типа элемента. Например, Text использует текстовое
содержимое, Image — источник изображения, а Button может объединять текст,
иконку, логотип и собственную картинку.

## 5. Appearance

`Appearance` задаёт внешний вид элемента:

- фон;
- цвет;
- граница;
- радиус скругления;
- тень;
- шрифт;
- прозрачность.

Appearance является данными Deck и не должен зависеть от WPF, WebView или
конкретного клиентского UI-фреймворка.

## 6. Behavior

`Behavior` описывает реакцию элемента на взаимодействие и изменение состояния:

- `Hover`;
- `Click`;
- анимации;
- состояния.

Для интерактивных элементов целевой набор состояний включает `Normal`,
`Hover`, `Pressed`, `Running`, `Success`, `Error` и `Disabled`. Конкретные
состояния должны быть отображаемыми данными, а не логикой отдельного клиента.

## 7. Почему Element отделён от Action

`Element` описывает визуальный объект и его поведение. `Action` описывает,
что должно произойти при взаимодействии, а Executor определяет, как это
выполнить.

Связь выглядит так:

```text
Element → Action → Executor → Result → State Update
```

Такое разделение позволяет одному Action использоваться разными типами
элементов, а одному Element работать в Desktop Preview и Web Runtime.
Оно также не заставляет декоративные элементы, например Text или Image,
иметь обязательную команду.

## 8. Типы элементов

Первый этап Designer:

- `Button` — интерактивный элемент;
- `Text` — текстовый блок;
- `Image` — изображение или ресурс;
- `Container` — группа и область для других элементов.

Будущие типы:

- `Widget`;
- `Chart`;
- `Status`;
- `Plugin Element`.

Новые типы должны использовать общий Element System и общий Renderer, а не
создавать отдельную модель или отдельный формат отображения.

## 9. Button Element

`Button` — полноценный визуальный и интерактивный объект.

### Внешний вид

Button может содержать:

- собственную картинку;
- логотип;
- иконку;
- текст;
- фон;
- размеры;
- стиль.

Эти данные относятся к Content, Appearance и Layout, а не к Executor.

### Поведение

Button должен описывать состояния и переходы для:

- `Hover`;
- `Pressed`;
- `Running`;
- `Success`;
- `Error`;
- `Disabled`.

### Action

Button может иметь привязанное действие, настроенное через Designer:

- выбор программы через диалог выбора файла;
- аргументы программы;
- запуск скриптов;
- URL.

Выбор программы и редактирование параметров являются частью Designer. Сам
Button не запускает процесс напрямую: выполнение проходит через Action System.

## 10. Связь с Renderer

Element является входными данными для двух представлений:

```text
Deck Model
    ↓
Element
    ↓
RadishDeck Renderer
    ├── Desktop Designer Preview
    └── Web Runtime
```

Renderer читает Identity, Layout, Content, Appearance, Behavior и состояние
элемента. Desktop Designer редактирует эти данные, Web Runtime показывает их.

Главный принцип: **What You See Is What You Get**. При одинаковом Deck и
Device Profile результат Preview должен соответствовать результату Web
Runtime.

## 11. Совместимость с текущей моделью

Текущий прототип использует плоские свойства:

- `GridX`;
- `GridY`;
- `GridWidth`;
- `GridHeight`;
- `ActionId`.

Их смысл можно сопоставить с целевой моделью следующим образом:

| Текущий прототип | Целевая модель |
|---|---|
| `GridX`, `GridY` | `Layout.Position.X/Y` |
| `GridWidth`, `GridHeight` | `Layout.Width/Height` после определения единиц Canvas |
| `ActionId` | ссылка или идентификатор в `Action` |
| `Type`, `Name`, `Id` | `Identity.Type`, `Identity.Name`, `Identity.Id` |

Переход должен выполняться поэтапно: загрузить старую модель, определить
Canvas и профиль устройства, сопоставить координаты и размеры с целевыми
единицами, затем сохранить новую структуру. Для `ActionId` потребуется
сохранить семантику действия и связать её с новой секцией Action.

Этот документ только фиксирует направление перехода. Миграция, изменение
`deck.v1.json`, новая схема Deck и обратная запись в текущий формат здесь не
реализуются.

## 12. Будущая JSON-форма

Пример будущего элемента:

```json
{
  "id": "element-restart-server",
  "type": "button",
  "name": "Restart Server",
  "layout": {
    "x": 100,
    "y": 200,
    "width": 300,
    "height": 100,
    "layer": 1,
    "alignment": "center"
  },
  "content": {
    "text": "Restart Server"
  },
  "appearance": {
    "background": "#E11D2E",
    "radius": 20
  },
  "action": {
    "type": "process.start"
  }
}
```

Это концептуальный пример будущей модели и не является текущим контрактом
`deck.v1.json`.

## 13. Правила развития

- Element остаётся платформенно независимой моделью данных.
- Renderer остаётся общим для Desktop Preview и Web Runtime.
- Action System не переносится внутрь Element.
- Новые типы не должны возвращать проект к Grid-only модели.
- Реализация новых полей начинается отдельной задачей после согласования
  формата Deck и плана миграции.
